# TROUBLESHOOTING — если что-то пошло не так

**Статус на сейчас:** проект собирается. Готовый `DotShell.exe` лежит в `release\`
(собран через `dotnet publish`, single-file, self-contained, win-x64). UI — WPF
(проект `DotShell.Island.Wpf`), Visual Studio не нужна, хватит .NET SDK 8.
Разделы ниже про WinUI 3 оставлены для архивного варианта `src\DotShell.Island\`.

**Главное правило:** сначала смотри `%LOCALAPPDATA%\DotShell\crash.log`,
потом — вывод `dotnet build` в консоли, и только потом гугли.

---

## Быстрый старт (копия из README)

```powershell
# из папки dotshell
dotnet build DotShell.sln -c Debug -p:Platform=x64
dotnet run --project src\DotShell.Island.Wpf\DotShell.Island.Wpf.csproj -c Debug
```


Или: открыть `DotShell.sln` в Visual Studio 2022 → выбрать **x64** →
правый клик по `DotShell.Island` → *Set as Startup Project* → **F5**.

## 0. Ошибки первой сборки (уже исправлены, но полезно понимать причину)

Это реальный список ошибок, который выдала первая сборка. Оставил его здесь,
потому что все четыре — типовые для такого проекта, и полезно знать, откуда они берутся.

### «Тип или имя пространства имен "Storage" не существует в пространстве имен "DotShell.Core.Windows"»
**(и то же самое для `Media`, `Graphics`, `ApplicationModel`)**

Самая коварная ошибка из всех. Я назвал папку и namespace `DotShell.Core.Windows` —
и этим **перекрыл глобальное пространство имён `Windows`**. Внутри файла, который лежит
в `namespace DotShell.Core.Windows`, запись `Windows.Storage.StorageFolder` ищется
как `DotShell.Core.Windows.Storage.StorageFolder` — а такого, конечно, нет.

**Урок:** никогда не называй namespace именем, совпадающим с корнем другого дерева
(`Windows`, `System`, `Microsoft`, `Media`, `Drawing`). Переименовал в
`DotShell.Core.Windowing`.

### «Несогласованность по доступности: доступность типа параметра "Win32.RECT" ниже доступности метода»
Класс `Win32` был `internal`, а публичный метод `WindowWatcher.TryGetExtendedBounds`
отдаёт `out Win32.RECT` наружу. Так нельзя: публичный метод не может показывать тип,
который снаружи не виден. Сделал `Win32` публичным — это всё равно внутренние
объявления Win32, скрывать их смысла нет.

### «Не удалось найти тип `GlobalSystemMediaTransportControlsSession` / `SessionsChangedEventArgs` / `IRandomAccessStreamReference`»
Это типы WinRT-проекции Windows SDK. В **библиотечном** проекте (`DotShell.Core`,
у которого нет своего UI) одного `<UseWinUI>true</UseWinUI>` иногда не хватает,
чтобы проекция подтянулась. Добавил в csproj явную ссылку:
```xml
<ItemGroup>
  <FrameworkReference Include="Microsoft.Windows.SDK.NET" />
</ItemGroup>
```

### «Комментарий XML не может содержать "--"» (MainPage.xaml, строка 140)
Я написал разделитель `<!-- ---------- СВЁРНУТОЕ СОСТОЯНИЕ ---------- -->`.
По стандарту XML последовательность `--` **запрещена внутри комментария**,
а `-` не может быть последним символом перед `-->`. Заменил дефисы на `=`.
Заодно выключил проверку XML во всех C#-комментариях (`NoWarn` в
`Directory.Build.props`) — там такие же разделители, и файл документации мы не генерируем.

### «Cannot resolve Assembly … DotShell.Core.dll»
Это **следствие** ошибок выше: ядро не собралось, поэтому остров не смог его найти.
Само пропало, как только починилось ядро. Такие «каскадные» ошибки всегда смотри
с конца: чини первую ошибку в списке, а не последнюю.

### Плюс одна мина, которую я убрал заранее
В `ShellServices` было свойство `public WindowWatcher Windows`.
Внутри этого класса любое обращение к `Windows.Media…` упало бы по той же причине,
что и первая ошибка: свойство `Windows` затеняет пространство имён.
Переименовал в `WindowWatcher` — чуть длиннее, зато невозможно выстрелить себе в ногу.

## 1. Ошибки при сборке

### `NU1102: не найден пакет Microsoft.WindowsAppSDK 1.6.241114003`
Я поставил конкретную версию, она могла устареть или не скачаться.
**Что делать:** Visual Studio → меню *Проект* → *Управление пакетами NuGet* →
вкладка *Обновления* → выбери любую доступную версию `Microsoft.WindowsAppSDK`
(1.5.x / 1.6.x / 1.7.x) и нажми «Обновить». То же самое для
`Microsoft.Windows.SDK.BuildTools`.

То же в консоли:
```powershell
dotnet add src\DotShell.Island package Microsoft.WindowsAppSDK
dotnet add src\DotShell.Core     package Microsoft.WindowsAppSDK
```

### `NETSDK1100: чтобы собрать проект для Windows, необходимо задать платформу`
Значит не выбрана архитектура. В Visual Studio в выпадающем списке платформ
(рядом с Debug/Release) выбери **x64**. В консоли — добавь `-p:Platform=x64`.

### `MSB3821: не удалось обработать файл … потому что он не входит в проект`
Редкий случай, если ты переносил папки. Пересоздай решение:
`dotnet new sln -n DotShell --force`, потом
`dotnet sln add src\DotShell.Core\DotShell.Core.csproj src\DotShell.Island\DotShell.Island.csproj`.

### `The Windows App SDK requires WindowsPackageType=None for unpackaged apps`
В `src/DotShell.Island/DotShell.Island.csproj` уже есть
`<WindowsPackageType>None</WindowsPackageType>`. Если студия всё равно ругается —
добавь ту же строку в `Directory.Build.props` внутри `<PropertyGroup>`.

### Ошибка про `Windows.Media.Control` / `GlobalSystemMediaTransportControlsSessionManager`
Это WinRT-проекция, она включается строкой `<UseWinUI>true</UseWinUI>` в csproj ядра.
Если её нет — добавь. Если есть и всё равно не находит — обнови
`Microsoft.Windows.SDK.BuildTools` до последней версии.

**Обратный случай:** если после добавления
`<FrameworkReference Include="Microsoft.Windows.SDK.NET" />` студия ругается на
дубликаты (`NETSDK1142` / «элемент уже включён») — просто удали этот `<ItemGroup>`
из `DotShell.Core.csproj`: значит, у тебя `UseWinUI` уже тянет проекцию сам.

### Ошибка про `System.Drawing` / `Graphics.CopyFromScreen`
Нужен пакет `System.Drawing.Common` в `DotShell.Core.csproj` (он там объявлен).
Если студия ругается на «платформозависимость» — добавь в csproj ядра:
```xml
<PropertyGroup>
  <EnableWindowsTargeting>true</EnableWindowsTargeting>
</PropertyGroup>
```

### `CS0104: "Color" является неоднозначной ссылкой`
Такое бывает, когда в файле одновременно `using Microsoft.UI;` и `using Windows.UI;` —
в обоих есть тип `Color`. **Убери `using Microsoft.UI;`** и оставь `using Windows.UI;`
(в проекте уже так сделано, но если добавишь новый файл с контролом — проверь).

### Ошибки вида `XamlCompiler error: x:Bind … не найден`
`x:Bind` проверяется на этапе генерации кода и очень строгий.
Чаще всего причина в том, что свойство во ViewModel не `public`,
или в пути опечатка. Читай сообщение целиком — там указан точный путь, который не нашёлся.

## 2. Собирается, но ведёт себя не так

### Остров не появился вообще
1. Смотри `crash.log` — если ядро не поднялось, там будет причина.
2. Диспетчер задач → есть ли процесс `DotShell.Island.exe`.
3. Если процесс есть, а острова нет: скорее всего окно улетело за пределы экрана
   (несколько мониторов с разным масштабом). Поставь в `settings.json`
   `"islandTopOffset": 10` и перезапусти; если не помогло — временно убери
   `WS_EX_TRANSPARENT` в `IslandChrome.Apply` (тогда окно станет кликабельным
   целиком и его будет видно по щелчку в Alt+Tab… хотя `WS_EX_TOOLWINDOW` его
   там прячет — закомментируй и его на время отладки).

### Появился серый/чёрный прямоугольник вокруг таблетки
Не погасили системную подложку окна. Проверь, что вызывается
`TrySetTransparentBackdrop()` в `IslandWindow`, и что `MainPage` имеет
`Background="Transparent"` (у неё есть). На старых сборках Windows атрибут
`DWMWA_SYSTEMBACKDROP_TYPE` (38) может отсутствовать — тогда помогает
явная установка `RequestedTheme="Dark"` у `RootGrid` и `Opacity` фона.

### По острову не получается кликнуть
Клики проходят насквозь, потому что окно создано с `WS_EX_TRANSPARENT`,
а «умный» hit-test его не снимает. Проверь:
1. `settings.json` → `"hitTestPollMs"` не должно быть `0` (по умолчанию 40).
2. В `IslandChrome.UpdateHitTest` сравниваются **физические** координаты.
   Если масштаб экрана не 100%, а `RasterizationScale` не определился
   (остался 1.0), область таблетки будет посчитана неверно.
   Быстрая проверка: выведи `_scale` в `StatusLine` — должно быть 1 / 1.25 / 1.5.
3. **Экспресс-костыль для отладки:** убери `WS_EX_TRANSPARENT` из `exStyle`
   в `IslandChrome.Apply`. Остров станет кликабельным всегда (и будет мешать
   кликам рядом с собой), зато сразу видно, в hit-test'е проблема или нет.

### Остров не кликается наоборот — перехватывает клики рядом с собой
Значит `WS_EX_TRANSPARENT` не снимается/не ставится. См. пункт выше.
Такое возможно, если `HitTestPollMs = 0` и флаг сняли вручную.

### Плеер пустой, хотя музыка играет
1. SMTC работает только с приложениями, которые **зарегистрировались** в системе.
   Проверь так: нажми `Win + Ctrl + N` (или открой панель громкости) — если там
   виден трек и кнопки, значит SMTC живой, и проблема в нашем коде.
   Если там пусто — приложение не отдаёт метаданные, мы бессильны.
2. Браузерный YouTube/Spotify Web отдают SMTC только во время реального воспроизведения.
3. В `StatusLine` (внизу раскрытого острова) должно быть имя процесса в `FOCUS:` —
   если там пусто, значит `WindowWatcher` не работает.

### Буфер обмена не пишет историю
1. `AddClipboardFormatListener` требует окно в том же потоке, где читают сообщения.
   У нас `NativeMessageWindow` создаётся в `ShellServices.InitializeAsync()`,
   который вызывается из `App.OnLaunched` — то есть в UI-потоке. Если ты перенёс
   создание ядра в фоновый поток, история работать не будет. Верни в UI-поток.
2. Проверь `crash.log` на `AddClipboardFormatListener failed`.
3. Убедись, что не запущено два экземпляра DotShell — они будут перехватывать
   уведомления друг у друга.

### Точки «мыльные» или разного размера при масштабе 125/150%
Значит сетка считается в логических пикселях, а растеризуется в физических.
В `DotTextBlock.RenderAsync` есть пересчёт через `XamlRoot.RasterizationScale`
и повторная проверка по `rtb.PixelWidth/PixelHeight`. Если у тебя масштаб
нестандартный (175%, 200%) — выведи `pixelW`, `cols`, `pitch` в лог и посмотри,
где расхождение. Лечится тем, что `cols` пересчитывается строго от `pixelW`.

### Часы не обновляются
`DotClockControl` тикает раз в 500 мс, но текст меняется только при смене минуты
(это намеренно — рендер точек не бесплатный). Проверь, что сработал `Loaded`
(подписка на таймер). Если контрол лежит в свёрнутой части острова и она
`Visibility=Collapsed` — `Loaded` может не произойти. У нас `CollapsedRow`
видим по умолчанию, так что это не должно мешать; но если ты поменял стартовое
состояние на раскрытое — проверь.

### Авто-цвет не работает / цвет странный
1. Вкладка «Тема» → «Авто-цвет из обоев» должен быть включён.
2. В `StatusLine` смотри `AUTO-COLOR: ON (уверенность 0.XX)`.
   Если уверенность < 0.06 — обои слишком серые/однотонные, цвет намеренно не меняется.
3. Как только ты кликнул пресет, авто-цвет **выключается** (иначе обои перекрасят всё
   обратно). Включи тумблер, чтобы вернуть.
4. Если обои — видео, цвет будет плавать. Это ожидаемо; сглаживание задаётся
   `"accentSmoothing"` в `settings.json` (меньше = плавнее).

### Программа жрёт CPU
Смотри, что тикает. Подозреваемые по порядку:
1. `EqDotsControl` — должен останавливаться, когда вкладка EQ не видна (`Eq.IsRunning`).
2. `AccentSampler` — не должен работать в fullscreen (`shouldSample`).
3. `_uiTimer` в `MainPage` — раз в секунду, это копейки.
4. `WindowWatcher` — раз в 300 мс, один `GetForegroundWindow` + пара вызовов, тоже копейки.

Правило: **любой таймер обязан останавливаться, когда его результат никто не видит.**

### Антивирус / SmartScreen ругается
На неподписанный self-contained `.exe` SmartScreen ругается всегда
(«Windows защитила ваш ПК») — это не значит, что программа вредная.
Для себя: «Подробнее» → «Выполнить в любом случае».
Для распространения: нужен сертификат подписи кода (платный, ~$100–400/год)
или публикация через Microsoft Store.

## 3. Как отлаживать такое, что не отлаживается обычным способом

Остров — окно без рамки, поверх всех, не берущее фокус. Ставить в нём точку
останова неудобно: пока дойдёшь до студии, состояние изменится.

Приёмы, которые тут реально помогают:

1. **Строка состояния вместо breakpoint'ов.** Внизу раскрытого острова есть
   `StatusLine`, куда уже выведены CPU, память, авто-цвет, акцент и фокусное окно.
   Добавляй туда что угодно — это быстрее, чем отладчик.
2. **Лог-файл.** `Log.Info("…")` пишет в `crash.log`. Для событий,
   которые происходят раз в несколько секунд, это удобнее консоли.
3. **Временный «обычный» режим.** Закомментируй в `IslandChrome.Apply`
   `WS_EX_TOPMOST | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_TRANSPARENT` —
   получишь обычное окно, которое ведёт себя предсказуемо и которое удобно отлаживать.
   Потом верни обратно.
4. **Spy++ / WinSpy** — посмотреть реальные стили и HWND окна, если кажется,
   что они не применились.
5. **Диспетчер задач → Подробности → добавить столбцы** «Поток GDI», «Поток USER» —
   если числу USER-объектов растёт, где-то утечка окон/таймеров.

## 4. Известные ограничения (это не баги)

- **Эквалайзер во вкладке EQ — визуализация.** Реальный системный звук он не меняет.
  Настоящий EQ подключается мордой к Equalizer APO (см. `ROADMAP.md`, шаг 5).
- **История буфера живёт только в памяти.** Перезапустил программу — история пуста.
  Это намеренно и ровно соответствует запросу «за сессию, пока компьютер не выключился».
  Постоянное хранение (SQLite) — шаг 6 роадмапа.
- **Заметки — один файл**, без папок и тегов. Специально.
- **Лаунчера пока нет.** Он следующий по плану.
- **Обоев пока нет.** Авто-цвет берётся со скриншота того, что сейчас на рабочем столе.
- **`RunAtStartup` пишет путь к `.exe`** в момент включения. Если перенесёшь папку
  программы — выключи и включи тумблер заново.
